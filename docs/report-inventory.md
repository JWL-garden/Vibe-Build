# 보고서 근거 현황표 (report-inventory)

> 작성일: 2026-10-08 · 기준 커밋 `c4eb259` · 기준 데이터 `261007-b` (source.json, 2026-10-07)
> 범위: 보고서에 나오는 **숫자와 그 근거만**. 페이지 구성·디자인·3D·UI 제외.
> 작성 방법: 실제 코드(lib/calc, lib/rules, lib/report, lib/data, components/report)를 읽고, `npx vitest run`(13파일 130개 통과)·`npm run data:check`(오류 0, 경고 1)를 실행해 확인했다.
> T1·T2 값은 runAll을 별도 스크립트로 실행해 뽑은 현재 값이다(코드 수정 없음). 모르는 값은 "확인 필요"로 적었다.

### 등급·용어

- **근거 등급**: A = 공식 데이터·법령 / B = 공개자료 기반 추정 / C = 프로젝트 가정 / D = 근거 없음(출처 없는 하드코딩·임의값)
- **테스트**: excelParity = 엑셀 대조 자동 테스트 / 손계산 = Vitest에 손계산 값 단언 / 없음
- **보고서 두 종류**가 있다. 이 문서는 ①을 기준으로 쓴다.
  - ① **기준 엑셀 필지 보고서** `/report?pnu=…` (T1·T2): `lib/report/buildSiteReport.ts` → `components/report/site/*` — 표지·1·2·3·5장·부록1·부록2. 4·6~10장은 "이어지는 장" 목록만 있다.
  - ② **S1 샘플 보고서** `/report?sample=S1`: `lib/mock/sampleReport.S1.json`(손으로 쓴 숫자) → `components/report/Ch00~Ch10, Appendix` — 0~10장이 모두 있지만 **runAll 결과가 아니다**(6장 끝 참고).

## 3. 데이터 검증 방법 현황

### 3-1. `npm run data:check` (scripts/check-data.mjs, 기준: lib/data/sheetMap.json)

1. 필수 시트 존재, sheetMap에 없는 시트 경고
2. 필수 컬럼(columns + key) 존재 — 없으면 비슷한 이름 제안
3. 키 중복(unique) — 키 빈 행은 경고 (현재 경고 1건: 건축물대장_2단계 관리건축물대장PK 빈 행 3개, T1·T2 아님)
4. T1·T2(examples.json의 '기준 엑셀' 태그) 행 존재 + targetRequired 칸 비어 있지 않음
5. 단위 이상값(min/max)·허용값(values) — **경고만**
6. 변환 JSON의 meta(fileHash·version)가 지금 엑셀과 같은지, T1·T2 포함 여부
7. siteInputs.json에 T1·T2 항목과 source(수기입력|확인필요) 존재 — 값 자체는 검사 안 함

### 3-2. excelParity (lib/calc/__tests__/excelParity.test.ts)

- 대상: '용적률완화_주차검토' 시트 중 판정 '미산정' 제외 **32행**, 시나리오 **B** 규칙으로 calcExpansion

### 5-2. 가정값 레지스트리 구조 (타입 초안 — 아직 코드 아님)

```ts
type Grade = 'A' | 'B' | 'C' | 'D'
type Unit = 'won' | 'wonPerM2' | 'rate' | 'months' | 'years' | 'multiple'

interface SourceRef {
  title: string          // 자료명
  publisher: string      // 발행기관
  baseDate: string       // 자료 기준일 (YYYY-MM-DD)
  url?: string
  note?: string          // 표본 수·기간 등
}

interface Assumption {
  key: keyof FinanceAssumptions
  label: string          // 보고서 표 이름 (assumptionLabels.ts 통합)
  unit: Unit
  base: number
  low?: number           // 보수 쪽 값 (임대료는 낮은 값, 공사비는 높은 값 — direction으로 해석)
  high?: number
  direction: 'higherIsBetter' | 'lowerIsBetter'   // ROI에 유리한 방향
  grade: Grade
  sources: SourceRef[]   // A·B는 1개 이상 필수
  reportText: string     // 보고서 표기 문구 (5-1 마지막 열)
  memo?: string
}

type AssumptionRegistry = Record<keyof FinanceAssumptions, Assumption>

// 필지별 시장 데이터 (market.json → 레지스트리 덮어쓰기용)
interface SiteMarketOverride { pnu: string; values: Partial<Record<keyof FinanceAssumptions, Pick<Assumption,'base'|'low'|'high'|'grade'|'sources'>>> }
```

흐름

1. `getFinanceAssumptions(pnu, userInput)` = **사용자 입력 > 필지별 시장데이터(market.json) > 레지스트리 기본값** 순으로 항목별 병합, 결과에 `origin: 'user'|'market'|'default'`와 최종 `grade`를 함께 남긴다 (사용자 입력은 grade 'C' + "사용자 입력" 표기).
2. runAll이 이 결과를 finance [A]~[D]에 넘기고, `SiteAnalysis.finance.assumptions`로 함께 반환.
3. buildSiteReport의 부록이 이 배열을 그대로 **가정값 표**(항목·값·범위·등급·표기 문구)와 **출처 표**(자료명·기관·기준일·URL)로 출력 — 보고서 컴포넌트는 계산하지 않음.
4. 기존 `landValueRule`·`buildingValueRule`도 같은 레지스트리 형태로 옮겨 재조달단가 D 문제를 같이 정리.

### 5-3. 불확실성 처리

- **보수/기준/낙관 자동 생성**: financeScenarios를 손으로 쓰지 않고, 레지스트리의 `low/base/high` + `direction`으로 만든다. 보수 = 모든 항목을 ROI에 불리한 쪽, 낙관 = 유리한 쪽. (설계서 6-2의 ×0.9·+5%p 같은 고정 배수는 범위가 없는 항목에만 기본값으로 사용)
- **토네이도**: 범위가 있는 항목마다 그 항목만 low/high로 바꿔 ROI 재계산 → 변동폭 큰 순 정렬.
- **등급 C 이하 영향 표시**: 토네이도 막대에 등급 배지. "등급 C·D 항목만 보수 쪽으로 바꿨을 때 ROI·회수기간"을 별도 1줄로 계산해 0장 결론 옆에 표시 ("가정 항목 영향: ROI x~y%"). 결론 지표 변동의 절반 이상이 C·D 항목에서 오면 결론 문장에 "가정 의존도 높음" 경고를 붙인다.

### 5-4. 검증 방법

- **손계산 기준 케이스**: T1(ALL, +99.27㎡ 3세대)·T2(ALL, +36.25㎡ 1세대) 각 1개. 가정값 확정 후 엑셀/손으로 사업비·NOI·ROI를 계산해 `finance.test.ts`에 단언 (값은 레지스트리 확정 후 작성).
- **합계 검산 (항상 성립)**: 사업비 항목 합 = 총사업비, 자기자본 + 대출 = 총사업비, ROI × 회수기간 = 1, 보수 ≤ 기준 ≤ 낙관(ROI), 증축 0이면 수익성 '증축 불가' 상태.
- **레지스트리 검사 스크립트** (`npm run assumptions:check`, data:check와 같은 방식): low ≤ base ≤ high, 단위별 허용 범위(비율 0~1 등), 등급 A·B는 sources 필수, baseDate가 기준일보다 N개월 이상 오래되면 경고, 등급 D 항목이 있으면 오류(보고서 완성 전 0개).
- **보고서 정합 테스트**: 0장 KPI = 4·5장 본문 = runAll 값 (buildSiteReport.test.ts에 추가).
